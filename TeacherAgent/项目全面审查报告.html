三、核心优势

  • 文档驱动开发执行力强：项目治理、Prompt 治理、Agent 架构、工具接口、数据模型、缓存策略、Rust 模块图、验证清单各司其职，且明确"冲突时以专项文档为准"，避免多头维护漂移。
  • 教学理念贯彻到代码：苏格拉底引导、提示阶梯 L0-L4、渐进妥协、复盘模式、学科风格矩阵（数学严谨 / 英语诙谐 / 法学会计审慎）均落到 subjectStyle.ts、socraticAgent.ts、Prompt Builder 和 Guardrail，而非停留在文档。
  • 护栏闭环完整且成本可控：规则初筛 → 风险时 LLM Guardrail → 最多一次 rewrite → 兜底模板，有确定终止路径；普通低风险轮次不增加 LLM 调用，符合"普通轮次 1-2 次、复杂 3 次"的调用预算。
  • API Key 主路径安全：keychain 存储 api_key_ref，SQLite 只存引用；Rust complete_llm_chat 从凭据库取 key 设 Authorization；前端 store 用 Omit<LlmProviderConfig,"apiKey"> 类型约束不持明文。
  • LLM 请求日志脱敏到位：provider.rs 的 redact_sensitive_text 清洗 Bearer/api_key token，host 去 query，不记录请求体/对话/画像。
  • 知识库 Pack 懒加载设计优秀：packManifest.ts + packLoader.ts 用 import.meta.glob 分 chunk，ChatView chunk 从 566 kB 降至 458 kB，内存 Map 缓存 + 预加载 API，实现质量高。
  • SQL 全部参数化 + LIKE 转义：params! 占位，private_doc.rs 对 % _ \ 转义防通配注入，动态 OR 子句只拼占位编号。
  • 迁移幂等：schema_migrations 表 + IF NOT EXISTS + INSERT OR IGNORE 守卫，4 个 migration 可重复执行。

四、风险与问题清单（按严重度）

P0 — 安全防御面（建议优先闭合）

P0-1 前端 LLM Provider 存在明文 Key 直连 fetch 分支
src/services/llm/openAiCompatibleProvider.ts:52-58 · src/services/llm/types.ts:12

当 config.apiKeyRef 为空但 config.apiKey 存在时，绕过 Rust complete_llm_chat，直接在前端用明文 key 发起 HTTP 请求。类型 LlmProviderConfig.apiKey?: string 留有后门字段，违反 governance §7.1"LLM 请求应优先通过 Rust command"。

  • 生产主路径（设置页保存→store 只给 apiKeyRef）不触发，但属于可被构造调用的泄露面。
  • 建议：移除 fetch fallback 分支，或仅限 isLocal=true（Ollama 无 key）场景；同时从 LlmProviderConfig 类型删除 apiKey? 字段，彻底闭合前端明文 key 路径。
P0-2 Rust load_provider_api_key 命令经 IPC 回传明文 Key
src-tauri/src/lib.rs:274-277 · src/services/tauri/commands.ts:307-311

该 command 返回 Result<Option<String>, String>，即明文 API Key 经 Tauri IPC 回到前端进程。前端封装 loadProviderApiKey(): Promise<string|null> 同样返回明文。

  • 当前缓解：全前端 grep 确认该函数未被任何调用方使用（死命令），所以是"潜在泄露面"而非"正在泄露"。
  • 仍违反 data-model.md §3.16"前端不保存明文 API Key"的契约精神——命令一旦注册即可被任意前端代码/插件调用。
  • 建议：删除该 command，或改为 has_provider_api_key(ref): Result<bool,String> 只回传存在性布尔值；前端"测试连接"已通过 complete_llm_chat 间接验证，无需取回明文。

P1 — 可维护性 / 健壮性债务

P1-1 lib.rs 体积过大（~2000 行 / 72KB），embedding 与 helper 未拆出
src-tauri/src/lib.rs:362-565 (generate_embedding/batch) · :960 (truncate_for_storage 重复)
  • embedding 相关约 200 行内嵌在 lib.rs，与 rust-module-map.md 既定拆分顺序不符（应拆 embedding.rs）。
  • truncate_for_storage 在 lib.rs 与 provider.rs 重复定义，应迁入 shared.rs。
  • 建议：按 rust-module-map.md §"下一步拆分顺序"第 4 步执行，先拆 shared.rs 再拆 embedding.rs。
P1-2 多个 View / Agent 文件过长，超 500 行
SettingsView.vue 1958 · ChatView.vue 1243 · KnowledgeGraphView.vue 953 · commands.ts 908 · plannerAgent.ts 773 · DocumentImportPanel.vue 713 · PracticeView.vue 690 · tutorOrchestrator.ts 687 · toolAgent.ts 670 · reflectionAgent.ts 564 · memoryService.ts 507
  • SettingsView 近 2000 行集中了数据库/Provider/知识库/资料管理多块职责，单文件回归测试成本高。
  • 建议：按职责拆子组件（ProviderCard / DatabasePanel / KnowledgeBasePanel / PrivateDocPanel）；ChatView 拆 composer / sidebar / message-list。
P1-3 tutorOrchestrator 的 handleTurn 与 handleTurnStream 约 250 行近乎重复
src/engine/agents/tutorOrchestrator.ts:72-255 vs :257-525
  • 两套方法各自重走 socratic → toolAgent → memory → planner → prompt → guardrail 流程，仅流式与非流式差异。后续任一分支改逻辑易漏改另一支。
  • 另：:74,82 的 timestamps 数组被 push 但从未读取（死状态，仅 onTiming 回调有用）。
  • 建议：抽取共享编排骨架 runTurnCore()，流式作为参数分支；删除死状态。
P1-4 核心 Agent 缺单元测试，与治理文档 §8.2 不符
plannerAgent.ts (773行) / assessmentAgent.ts / reflectionAgent.ts (564行) 均无单测
  • governance §8.2 明确"教学引擎核心逻辑需要单元测试"。Planner 读取掌握度/前置依赖/复习到期，逻辑复杂度高却无测试保护。
  • 建议：优先补 plannerAgent（事件触发判定、复习到期阈值、前置依赖回退）与 assessmentAgent（正确性分类、掌握度 delta）测试。
P1-5 CompleteLlmChatOutput.raw 将整包 provider 响应回传前端
src-tauri/src/provider.rs:458 · provider 流式/非流式输出 DTO
  • raw 字段把完整 JSON 响应体送回前端进程，若某 provider 在响应中回显敏感字段（如请求 echo、账户信息）会扩大前端暴露面。
  • 建议：评估前端是否真需 raw；若仅调试用途，改为 dev feature 或白名单字段提取。
P1-6 依赖偏重：tokio full + reqwest blocking 并存
src-tauri/Cargo.toml:23-24
  • tokio 开 full 偏重，reqwest blocking 仅 ollama.rs:6 使用，与流式异步路径并存造成两套运行时模型。
  • 建议：tokio features 收窄（rt-multi-thread, macros, sync, time）；ollama 调用改异步统一，移除 blocking。

五、维度详评

1. 架构与边界 优

五层架构（表现/教学引擎/AI服务/数据/基础设施）落地清晰。表现层基本不直接访问数据库或 Provider——ChatView 通过 tutorOrchestrator.handleTurn() 调用，符合 governance §4.1。唯一轻微越界：LearningPathPanel.vue 直接调 loadStudentKnowledge Tauri command（治理允许表现层调 command，但更规范经 service）。Pinia store app.ts 仅 59 行纯状态编排，无业务算法，合规。

2. 代码质量 良

TypeScript strict: true 已启用；生产代码 any 仅 1 处（submitPracticeAnswer.ts:26 mock）。无 console.log 残留（仅 console.warn 降级日志）。主要债务是超长文件与 orchestrator 重复（见 P1-2/P1-3）。Rust 侧 unwrap/expect 仅出现在 #[cfg(test)] 与启动路径，无敏感信息泄漏。

3. 安全与隐私 需加固

主路径（keychain + Rust 代理请求 + 脱敏日志）设计正确且执行到位。问题集中在两处"防御面"：前端 fetch fallback（P0-1）与 Rust 明文回传命令（P0-2，当前死命令）。两者都不在主流程触发，但违反"最小暴露"原则，建议优先闭合。其余：SQL 全参数化、LIKE 转义、sidecar 用 Command::new+args 数组无 shell、文件路径扩展名白名单——均安全。

4. 教学策略 优

护栏闭环（规则→LLM→rewrite→fallback）有确定终止；提示阶梯 L0-L4 + 渐进妥协 + 复盘模式均有代码实现；学科风格矩阵（数学 rigorous_patient / 英语 light_witty_coach / 法学 serious_fair_examiner）落到 subjectStyle.ts 并注入 Prompt Builder；outline_summary intent 覆盖资料大纲查询避免误触苏格拉底反问；私有资料引用强制"你的资料中提到…"表达防伪装公共知识。教学策略是本项目最扎实的维度。

5. 数据模型 优

19 张表与 data-model.md 一致；建表顺序已处理外键依赖（content_sources 先于 knowledge_nodes/questions）；迁移幂等；私有资料 hard delete + 同事务清理会话绑定；冷启动掌握度 0.5 避免新学生误判薄弱。向量库选型边界（Phase0 keyword mock → Phase1 sqlite-vec → 后续 LanceDB）清晰，且明确"完整 prompt 不进向量库"。

6. 依赖与构建 良

Vite 6 + Vue 3.5 + Vuetify 3.7 版本现代；Shiki 按需懒加载常用语言避免全量包；Pack 懒加载 chunk 拆分有效。Rust 侧 sqlite-vec 因 Windows 编译问题注释禁用并降级 brute-force，处理透明。债务：tokio full + reqwest blocking 偏重（P1-6）；无 tauri-plugin-sql（直接用 rusqlite，与"Rust 负责数据库"一致，非问题）。

7. 测试 中

前端 33 个测试文件覆盖 orchestrator/socratic/guardrail/toolAgent/packValidator/packLoader/promptBuilder/vectorSearch；Rust 覆盖迁移幂等/CRUD/keychain 拒明文/MiMo 兼容/向量/私有文档/seed 健康检查；Python worker 43 条。缺口：plannerAgent/assessmentAgent/reflectionAgent 无单测（P1-4）；UI 端到端验证因 Computer Use 失败仍待人工（已记入 verification-checklist）。

8. 文档一致性 良

15+ 契约文档 + 权威边界声明是行业少见水平。小瑕疵：Agent 命名风格、Tailwind 声明、rust-module-map 测试数、design.md 旧表述（P2-1~P2-4）需同步。open-decisions.md 集中管理未决项，避免假设散落，做法优秀。

9. 性能 良

ChatView chunk 458 kB 低于 500 kB 阈值；知识图谱切页 setTimeout(0) 让首屏先渲染 + Pack 并行 Promise.allSettled 加载已优化；LLM Reflection 改 fire-and-forget 不阻塞前台。待办：seed embedding 生成后向量检索真实链路；sqlite-vec ANN 索引（待 crate 修复）。

六、优先改进路线

  1. 闭合 API Key 防御面（P0，1-2h）：移除 openAiCompatibleProvider.ts fetch fallback 或限 isLocal；从 LlmProviderConfig 删 apiKey? 字段；将 load_provider_api_key 改为 has_provider_api_key: bool 或删除。
  2. 补核心 Agent 单测（P1，半天）：plannerAgent 事件触发/复习到期/前置回退；assessmentAgent 正确性分类与 delta。
  3. 拆 lib.rs（P1，半天）：先迁 shared.rs（含 truncate_for_storage 去重），再迁 embedding.rs。
  4. 重构 tutorOrchestrator（P1，1天）：抽取 runTurnCore() 消除 handleTurn/handleTurnStream 重复，删除 timestamps 死状态。
  5. 拆超长 View（P1，分批）：SettingsView 拆 4 个子面板，ChatView 拆 composer/sidebar/list。
  6. 依赖瘦身（P1，低优先）：tokio features 收窄，reqwest blocking 改异步。
  7. 文档同步（P2，随手）：命名约定、Tailwind、rust-module-map 测试数、design.md 顶部提示。
  8. 推进向量 RAG 闭环：生成 seed embedding + 接入向量检索真实链路（项目下一步主线）。

七、结论

TeacherAgent 是一个治理水平明显高于同类学生项目的工程：文档契约严密、教学理念贯彻到代码、隐私主路径设计正确、护栏闭环完整。当前不存在阻断性缺陷，处于"已可进入用户实机验证"的健康阶段。

最值得处理的不是功能，而是两处 API Key 防御面（P0-1/P0-2）——它们虽不在主流程触发，但违背项目自己写下的隐私契约，建议在进入下一轮功能开发前优先闭合，以维持"隐私不倒退"原则的可信度。其余均为常规可维护性债务，可按优先级分批消化。

项目下一步主线（seed embedding + 向量 RAG 闭环 + Ollama 实机）方向正确，建议在补齐安全加固后推进。
