## 项目概述

TeacherAgent 是一款面向全学科学生的桌面 AI 辅导助手。它的核心理念是"引导而非告知"——通过苏格拉底式对话引导学生自主发现答案，同时结合结构化知识库确保教学内容的准确性。

目标用户：大学生和考研备考者。大学生有自主终端设备（笔记本/台式机），学习时间灵活，对 AI 工具接受度高。核心场景包括：大学课程辅导（高数、线代、概率论、专业课等）、考研全科备考、各类资格证考试准备（CPA、法考、教资等）。

核心价值：让每个学生都拥有一个耐心、专业、了解自己的 AI 老师。

## 技术选型

### 框架：Tauri 2.x

经过对 Tauri 2.x 和 Electron 的对比分析，选择 Tauri 作为桌面框架，原因如下：

Tauri 的运行时内存占用约 30-40 MB，而 Electron 约 200-300 MB。对于需要本地运行 LLM（7B 模型需要 4-8 GB 内存）的应用来说，省下的 200+ MB 可能意味着能在 7B 和 3B 模型之间做出选择。安装包体积方面，Tauri 约 5-10 MB，Electron 约 100-150 MB，在教育场景中分发优势明显。

Tauri 的 sidecar 机制天然支持嵌入 Ollama 或 llama.cpp 二进制文件，这在 2026 年已成为 AI 原生桌面应用的主流模式。安全方面，Tauri 默认拒绝前端访问系统资源的模型，对处理学生数据的场景更为友好。

需要接受的代价：后端使用 Rust，学习曲线较陡；WebView 跨平台渲染可能存在细微差异。

### 前端：Vue 3 + TypeScript

选择 Vue 的原因：单文件组件（SFC）将模板、逻辑、样式集中在一个 `.vue` 文件中，结构清晰直观；响应式系统天然适合数据驱动的 UI（学生掌握度变化时仪表盘自动更新）；Vite 是 Vue 团队原生打造的构建工具，开发体验极佳。组件库选择 Vuetify 3，利用其 Material Design 组件、主题系统、导航、表单和数据展示能力，加速桌面应用界面开发。配合少量自定义 CSS 做布局、密度和领域化视觉调整。

### 数据存储

SQLite 通过 tauri-plugin-sql 集成，用于存储学生档案、对话历史、学习进度等结构化数据。向量数据库选用 SQLite-vec（SQLite 扩展），用于知识库的语义检索，避免引入额外的独立服务。

### AI 运行时

本地推理使用 Ollama 作为 sidecar 进程，通过其 HTTP API 调用。同时预留云端 API 适配器（OpenAI / 智谱 / DeepSeek），在网络可用时切换至更强模型。

## 系统架构

系统分为五层，从上到下依次为表现层、教学引擎层、AI 服务层、数据层和基础设施层。详细的可视化架构图见 `docs/architecture-diagram.html`。

### 表现层 (Presentation Layer)

表现层负责所有与学生的交互界面，包含四个核心模块：

对话界面是主交互通道，学生在此提问、讨论、接受引导。需要支持 Markdown 渲染、KaTeX 公式、代码高亮、图片上传。消息气泡区分学生和老师角色，老师的引导消息带有打字动效。

知识面板展示当前学习主题的知识点结构，以思维导图或概念卡片形式呈现。随着对话推进，相关知识点会自动高亮或展开。

练习模块提供题目练习与即时反馈。支持选择题、填空题、解答题等多种题型。解题过程支持分步骤展示，学生可以在任意步骤获得提示。

学习仪表盘呈现学习统计数据：今日学习时长、知识点覆盖率、各科掌握度雷达图、学习趋势折线图。仪表盘数据同时反馈给教学引擎，影响难度和路径决策。

### 教学引擎层 (Pedagogical Engine)

这是系统的"大脑"，决定教什么、怎么教。四个组件协同工作：

苏格拉底对话管理器控制对话策略。核心原则是不直接给出答案，而是通过追问引导学生思考。具体策略包括：探测性追问（暴露推理漏洞）、分解引导（拆解复杂问题）、反例探索（发现错误方法的后果）、反思性提问（审视自己的思维过程）、类比桥接（从已知迁移到未知）。

脚手架控制器管理帮助的"粒度阶梯"。每个问题准备从最宽泛到最具体的多级提示，学生卡住时逐级升级提示的具体程度。随着学生掌握度提高，脚手架逐步"淡出"（fading），减少支持力度。

学习路径规划器基于知识图谱生成个性化的学习序列。它考虑前置知识关系（学 B 之前需掌握 A）、学生当前的知识状态（从学生模型读取）、以及学习目标（考试准备 / 薄弱点补强 / 拓展学习）。

护栏引擎在多个层面执行安全策略：system prompt 层约束 LLM 行为；输出过滤层检测是否直接给出了答案（如检测到完整解题过程则拦截并重写为引导性问题）；对话策略层检测学生是否在要求直接给答案并做柔性拒绝。

### AI 服务层 (AI Service Layer)

这一层是 LLM 能力的封装和调度中心。

LLM 适配器提供统一接口，屏蔽本地 Ollama 和各类云端 API 的差异。支持运行时切换模型、自动降级（云端不可用时切本地）、流式输出。

API 兼容策略采用"OpenAI 格式优先"原则。OpenAI 的 Chat Completions 格式已成为事实行业标准，国内主流服务商（DeepSeek、智谱 GLM、通义千问、月之暗面 Moonshot、零一万物）均提供兼容接口，本地 Ollama 也暴露 OpenAI 兼容端点（`localhost:11434/v1`）。这意味着用户只需配置 `baseUrl` + `apiKey` 两项参数，即可接入几乎所有服务商。适配器内部只需实现一套 OpenAI 格式的请求/响应/流式处理逻辑，通过切换 `baseUrl` 实现服务切换。

对于非 OpenAI 格式的 API（如 Anthropic Claude），在架构上预留 Provider 扩展接口。每种 Provider 实现一个适配器类（`OpenAIProvider`、`AnthropicProvider`），遵循统一的 `LLMProvider` 接口。初期只实现 `OpenAIProvider`，后续按需添加其他 Provider，不影响已有功能。

用户侧的配置模型：在设置页面中，用户可以选择"本地模式"（自动连接 Ollama）或"云端模式"（填写 baseUrl、apiKey、模型名称）。支持保存多个配置预设，一键切换。首次使用时，默认以本地 Ollama 为优先，若检测不到 Ollama 进程则引导用户配置云端 API。

RAG 检索器在知识库中检索与当前对话相关的内容（概念定义、例题、解析），注入到 LLM 上下文中。这确保 LLM 的回答基于权威教学内容，减少幻觉。检索策略：先用 embedding 做语义相似度检索，再用知识图谱做结构化关联。

学生模型追踪器维护每个学生的知识状态。采用混合方案：对结构化的技能点使用 BKT（贝叶斯知识追踪）跟踪掌握概率；对开放式对话使用 LLM 分析对话信号（犹豫、误解模式、参与度）。追踪结果注入每次 LLM 调用，使导师能自适应调整策略。

Prompt 构建器将上述所有信息组装成最终的 LLM 请求：系统角色（导师人格）+ 教学规则（不给答案、用提问引导）+ 学生上下文（知识状态、近期表现）+ 领域知识上下文（RAG 检索结果）+ 对话历史。

### 数据层 (Data Layer)

知识图谱以结构化方式表示课程内容：概念节点、前置依赖关系、课程大纲对齐。支持按学科/课程/章节组织。初期可从大学通用教材目录和考研大纲构建骨架，逐步丰富。

题库包含题目、解析、难度标签、关联知识点。支持多种题型。解析需要包含分步骤的解题思路，以配合脚手架控制器。

学生档案存储学习历史、各科掌握度、学习偏好（偏好的讲解方式、活跃时段等）、错题记录。

对话记录保存完整的师生对话，既用于对话连续性，也用于学生模型的持续更新。

### 基础设施层 (Infrastructure)

Tauri 2.x Runtime 提供 Rust 后端和系统 WebView 渲染。SQLite 作为主数据库。SQLite-vec 扩展提供向量检索能力。Ollama 作为 sidecar 进程运行，随应用启动和管理。

## 核心功能模块

### MVP 阶段（第一期）

MVP 聚焦于验证核心教学体验，包含三个最小可用功能：

第一，对话式辅导。学生输入学科问题，AI 以苏格拉底方式引导。支持文本输入和基本的 Markdown/公式渲染。这是产品的核心差异化功能，必须第一个做好。

第二，基础知识追踪。记录学生在对话中展示出的知识点掌握情况（通过 LLM 判断回答正确性 + 识别涉及技能），在侧边栏显示简单的掌握度进度条。

第三，本地知识库。预装一个学科（建议从数学开始，因其知识结构最清晰）的基础知识点和例题数据，以 JSON 格式存储，支持 RAG 检索。

### 第二期

在 MVP 验证核心体验后，扩展以下能力：

练习模式——从题库中按知识点/难度推荐题目，支持分步骤提示。学生仪表盘——可视化学习进度、知识覆盖率、薄弱点分析。知识图谱可视化——在知识面板中展示概念关系图，已掌握/进行中/未学习的节点用不同颜色标识。多模态输入——支持拍照识别题目（OCR）、语音输入。

### 第三期

进一步完善和扩展：

多学科支持——扩展知识图谱和题库覆盖语文、英语、物理、化学等。自适应学习路径——基于学生模型自动生成每日学习计划。家长/教师模式——可查看学生的学习报告和高频错题。离线模式优化——确保在无网络环境下完整可用。

## 核心交互流程

### 辅导对话流程

学生提出一个问题（例如："这道求极限的题怎么做？lim(x→0) sin(x)/x"）。系统执行以下步骤：

首先，学生模型追踪器读取当前学生的知识状态，发现该学生在"等价无穷小替换"上掌握度较低（0.3）。

然后，RAG 检索器从知识库中找到相关的知识点（夹逼定理、等价无穷小、洛必达法则）和类似例题。

接着，Prompt 构建器组装 prompt：导师角色 + 苏格拉底策略 + 学生当前水平（等价无穷小替换薄弱）+ 检索到的知识上下文 + 最近对话历史。

LLM 生成引导性回复，例如："这个极限是经典的 0/0 型不定式。在直接代入之前，你觉得分子 sin(x) 在 x 趋近于 0 时的行为和 x 本身有什么关系？能不能从图像或直觉上想一想？"

护栏引擎检查输出：确认没有直接给出答案，没有不恰当内容，通过后展示给学生。

学生回答后，学生模型追踪器更新其知识状态，整个过程循环往复。

### 练习模式流程

学生选择知识点和难度 → 系统从题库推荐题目 → 学生作答 → 系统判断正确性 → 如果错误，脚手架控制器按提示阶梯给出第一级提示（最宽泛的引导） → 学生再次尝试 → 如仍卡住，升级提示具体程度 → 最终解决后更新学生模型。

## 教学策略设计

### 苏格拉底对话的五种策略

探测性追问：在学生给出回答后，提出暴露推理漏洞的后续问题。比如学生说"答案是 6"，追问"你是怎么得到 6 的？能说说你的思路吗？"

分解引导：当学生面对复杂问题无从下手时，将其拆解。"这个问题看起来有点复杂。我们先看第一步：你觉得这里涉及哪些数学概念？"

反例探索：引导学生发现方法的缺陷。"如果按你刚才的方法，当 x 是负数的时候会发生什么？"

反思性提问：推动学生审视自己的思维过程。"你选择用洛必达法则而不是等价无穷小替换，是什么让你觉得洛必达在这里更合适？两者适用的条件分别是什么？"

类比桥接：从学生已掌握的知识出发。"你已经知道一元函数的导数表示切线斜率，那多元函数的偏导数你觉得在几何上应该怎么理解？它和一元的情况有什么联系和区别？"

### 提示阶梯设计

每道题准备 4 级提示，从宽到窄：

Level 0（无提示）：学生独立尝试。
Level 1（方向性提示）："这道不定积分可能需要用换元法，你觉得选什么作为 u 比较合适？"
Level 2（方法性提示）："观察被积函数的结构，里面有 e^x 和多项式的乘积，试试分部积分法？想想 u 和 dv 分别选什么。"
Level 3（接近答案的提示）："令 u = x², dv = e^x dx，分部积分后你会得到一个新的积分，这个积分还需要再做一次分部积分，试试看？"

### 护栏机制

输出过滤器检测 LLM 回复是否包含完整的解题过程或最终答案。检测方式包括：正则匹配答案格式（如 "= 42"）、LLM 自身判断（用小模型快速分类"此回复是否直接给出了答案"）。若检测到直接答案，则拦截并用引导性回复替代。

对话策略层维护一个"拒绝计数器"。当学生连续要求直接给答案时，导师不会简单拒绝，而是渐进妥协：第一次柔性引导，第二次给出部分信息加引导问题，第三次给出关键步骤但保留最后一环让学生完成。

PracticeSession（练习会话）：id, student_id, questions[], results[], started_at, finished_at

关系型数据（学生、题目、对话等）存储在 SQLite。知识图谱使用邻接表模型存在 SQLite 中（KnowledgeNode + prerequisite 关系表），简单高效。向量嵌入使用 SQLite-vec 扩展，与主数据库同文件，简化管理。

## 自适应递归学习机制

这是让 TeacherAgent 真正区别于普通 AI 对话的核心能力——"越用越懂你"。

### 核心理念

每次对话结束后，系统自动从交互中提取学生的认知信号，沉淀为长期记忆。下次对话时，这些记忆被检索出来注入上下文，形成一个不断自我强化的反馈闭环。

这不是简单的"记住聊天记录"，而是对学生的理解逐层加深：从"这个知识点会/不会"到"这个学生的思维习惯是什么、容易在哪里卡住、什么样的讲解方式对他最有效"。

### 递归提取流程

每轮对话结束后，后台自动执行一次"反思"（Reflection）过程：

第一步，知识状态更新。从对话中识别涉及的知识点，结合学生的回答质量（正确性、完整度、犹豫程度）更新 BKT 掌握概率。这是结构化层面的更新。

第二步，学习画像丰富。用 LLM 对整段对话做摘要分析，提取非结构化的认知特征：思维模式（"倾向于直觉推理，不太注重严谨步骤"）、常见误解模式（"容易混淆函数的定义域和值域"）、学习风格偏好（"喜欢用生活类比来理解抽象概念"）、注意力特征（"连续讨论超过10分钟后回答质量下降"）。

第三步，教学策略调优。记录哪些引导策略对这个学生有效（"用反例引导比直接追问效果好"），哪些题目难度匹配得当（"难度3的题目在这个掌握度下最能激发思考"）。这些经验直接影响后续对话的策略选择。

### 向量存储与检索

上述提取出的认知特征以 embedding 形式存入 SQLite-vec。检索时不只是按相似度匹配，而是按维度分类召回：知识维度（当前讨论的知识点相关历史）、风格维度（这个学生的学习偏好）、策略维度（过去有效的教学方法）。三类召回结果分别注入 prompt 的不同位置。

随着使用时间增长，向量库中积累的"学生认知档案"越来越丰富，AI 导师的个性化程度也随之提升。这就是"递归"的含义——每一次交互都在加深系统对学生的理解，而这个理解又让下一次交互更加精准。

### 遗忘与衰减机制

学生的认知状态不是静态的。长期未接触的知识点掌握概率会自然衰减（遵循艾宾浩斯遗忘曲线的近似模型）。系统定期对向量库中的记忆做时效性加权，近期交互的权重高于早期交互。当检测到某知识点长时间未复习且掌握度下降时，主动建议复习。

## 目标导向学习路径

### 学习目标建模

支持学生设定宏观学习目标，如考研数学一、考研数学三、CPA 会计、法考等。每个目标对应一个完整的知识图谱子图，包含所有需要掌握的知识点及其前置依赖关系。

目标的定义方式：管理员（或未来的社区贡献者）基于考试大纲和主流教材，将考试涉及的知识体系组织为有向无环图（DAG）。每个节点标注预估学习时长和难度等级（1-5）。

例如"考研数学一"这个目标，会展开为：高等数学（极限与连续 → 一元微分 → 一元积分 → 多元微分 → 多元积分 → 无穷级数 → 常微分方程）+ 线性代数（行列式 → 矩阵 → 向量 → 线性方程组 → 特征值 → 二次型）+ 概率论（随机事件 → 随机变量 → 多维分布 → 数字特征 → 大数定律 → 参数估计）……每个分支内部又有前置依赖和推荐学习顺序。

### 路径生成算法

设定目标后，系统执行以下步骤生成个性化学习路径：

首先做能力定位。通过对话式评估（见下节）确定学生在目标知识图谱中的当前位置——哪些节点已掌握、哪些部分掌握、哪些完全未接触。

然后做路径规划。从当前位置到目标终点，用拓扑排序生成基础路径，再根据以下因素做个性化调整：已掌握的前置知识可以跳过；部分掌握的节点安排复习巩固而非全新学习；根据学生的历史学习速度估算每个节点的预计耗时；根据遗忘曲线在合适的时间点插入复习节点。

最终输出一份可视化的学习计划：总进度条、每周建议学习内容和时长、里程碑节点（"完成高数一元微分模块后，你将覆盖考研数学一约 20% 的知识点"）。

### 动态调整

学习路径不是固定的。系统根据实际学习情况持续调整：某个知识点学得比预期快，后续内容提前推进；某个知识点卡住了，自动补充前置知识或推荐更多练习；学生新增了一个目标，系统在已有路径基础上找到可以合并的部分，避免重复学习。

### 难度递进策略

每个知识点内部也有从简到难的层次。系统的脚手架控制器配合难度标签，确保学生在每个阶段都面对"刚好超出当前能力一点点"的挑战（维果茨基的"最近发展区"理论）。具体实现：题目按难度 1-5 分级，系统从学生当前掌握度推算合适的起始难度，正确率高且用时短则升级，连续错误或犹豫则降级。

## 对话式能力评估系统

### 评估触发时机

三种场景下触发评估：

首次使用时，做一次全面的"入学测试"。通过 5-10 分钟的对话，快速定位学生在目标学科的大致水平。这不是传统的"做一套卷子"，而是自然的对话："你觉得自己在数学方面哪些部分比较有信心？哪些部分觉得有点吃力？"然后针对回答做进一步探测。

设定新目标时，做一次目标相关的定位评估。比如学生设定了"考研数学一"目标，系统评估他在高数、线代、概率论各模块的当前水平，生成起点画像。

周期性复盘评估。每学习一段时间（如每周或每完成一个模块），系统在日常对话中自然穿插回顾性问题，检测是否有遗忘或理解深化，更新知识状态。

### 评估方法

评估不是"出题-做题-判分"的传统模式，而是融入对话的自然过程：

开放式提问："你能用自己的话解释一下什么是函数的单调性吗？"——评估概念理解深度，不只看对不对，还看解释的准确性和完整性。

诊断性追问："如果 f(x) = x² 在 x < 0 时是递减的，你怎么理解'递减'在这里的含义？"——探测理解的具体边界在哪里。

错误分析：给出一个有陷阱的说法让学生判断："有人说因为 lim(x→∞) sin(x)/x = 0，所以 lim(x→0) sin(x)/x 也等于 0，你觉得这个推理哪里有问题？"——通过学生对错误观点的反应，评估批判性思维和概念稳固度。

信心校准：学生回答后追问"你有多确定？"——区分"知道但不确定"和"确实掌握"，前者需要巩固信心，后者可能已经可以推进。

### 评估结果输出

每次评估生成一份结构化的能力报告，包含：各知识点的掌握度雷达图（直观展示强项和薄弱点）、整体水平定位（如"高数基础扎实，线代特征值部分需要重点突破，概率论多维分布概念模糊"）、建议的学习优先级排序、与目标之间的差距量化。

报告同时反馈给教学引擎，直接影响后续对话的难度选择、引导策略和题目推荐。

### Phase 4: 多学科与优化（持续）

扩展其他学科的知识图谱和题库。多模态输入（OCR 识题、语音）。性能优化（大模型推理加速、数据库查询优化）。自动更新机制。

## 风险与应对

LLM 直接给出答案：多层护栏（prompt 约束 + 输出检测 + 策略引擎），持续测试迭代 prompt。

本地模型能力不足：默认使用云端 API，本地模型作为离线备选。随硬件发展逐步提升本地模型权重。

知识库质量：初期人工审核确保知识点准确，后期引入社区贡献 + 审核机制。

Rust 学习成本：可先用 TypeScript 编写核心教学引擎逻辑，通过 Tauri IPC 调用；Rust 后端初期只做最小化的数据库和 sidecar 管理。

学生数据隐私：全部数据本地存储，不上传云端。如未来需要云同步，采用端到端加密。

## AlertTime 单手机局域网同步扩展（可选，2026-08-03 用户授权）

> 本扩展是用户明确授权的可选项，不改变「桌面优先、本地优先、云端增强、隐私不倒退」的产品原则；它**不是**公网多端同步。实现契约以 `docs/decisions/2026-08-03-alerttime-lan-sync.md` 和 `sync/protocol/protocol.md` 为准。

### 场景

学生用 Android 端 AlertTime 记录科目、周目标、执行计划、计划完成状态、学习会话与有效学习时长；在家庭 WiFi 或手机热点下，手动触发「立即同步」，把执行数据上报给桌面 TeacherAgent。TeacherAgent 展示周完成情况（区分计划完成率与学习投入度）、按用户显式映射的学科用 approved 题库诊断、根据真实答题结果判断掌握情况，并生成学习计划建议稿（proposal）下发给手机。手机端明确点击「采纳」后才创建本地周目标与 `type=1` 计划；后续快照携带可选 `sourceProposalId`，TeacherAgent 经 accepted proposal 精确交叉核验后展示执行反馈，并把最近一次可追踪结果用于下一轮建议。TeacherAgent 不得直接覆盖手机现有计划，来源字段本身不得被解释为完成证据。

### 交互流程

```text
AlertTime（手机）                        TeacherAgent（桌面）
    │  用户开启局域网同步服务（默认关闭）          │
    │        生成自签证书（keychain）+ 配对二维码    │
    │  ←—— 二维码：HTTPS 地址、端口、证书 pin、一次性 token、过期时间 ——│
    │  扫描二维码 → 确认配对 → POST /v1/pair       │
    │  换发长随机设备凭据（Keystore 保护）           │
    │  立即同步 → POST /v1/snapshots（完整业务快照） │
    │  ←—— ack + GET /v1/proposals（建议稿） ——│
    │  展示建议 → 采纳/拒绝 → POST /v1/proposal-decisions │
```

### 数据所有权

- AlertTime 唯一权威：手机科目、周目标、任务、任务完成状态、学习会话、实际学习时长。
- TeacherAgent 唯一权威：周分析、诊断结果、掌握度、计划建议稿、建议理由、建议版本。
- 禁止两端自由编辑同一实体；TeacherAgent 下发的必须是 proposal（proposalId、rationale、proposedWeeklyGoals、proposedTasks、sourceAssessmentIds、status），而不是 TaskEntity。Android 采纳后创建的实体仍由 Android 管理；`sourceProposalId` 只记录创建来源，字段漂移、重复或旧客户端缺失时执行统计 fail-closed，不反向改写手机数据。

### 教学边界

- 学科映射必须由用户显式确认；AlertTime 自定义科目不得静默映射到知识节点；无映射时只分析执行情况，不更新掌握度。
- 掌握度只由 approved 题库的答题、诊断和明确评估证据驱动（现有 `assessment_results` + `student_knowledge` 链路）；学习时长只影响投入度判断；未答题不得更新 mastery；不绕过 GuardrailAgent。
- PlannerAgent 只在主动规划、诊断完成或阶段完成时触发；周目标表示本周结果目标，任务表示执行计划，不强制拆成固定每日任务，考虑休息日和特殊情况。

### Android 可选学习分析（2026-08-09 用户窄范围授权）

原“手机端不做 LLM”仍是默认边界；唯一例外是用户在 Android 独立设置中自行配置 Provider 后主动生成学习分析。该功能不依赖 Teacher 配对或桌面在线，先在手机保存用户画像（事实与推断分离）、计划合理性评估和无答案自评题草稿；每次新客户端同步再生成绑定本次快照的新分析。LLM 不可用时由确定性规则生成同结构结果。

- Android 不内置 Provider 地址、模型或公共 Key。用户可填写学习目的、考试/项目、考试科目和目标日期，字段默认留空；主动生成或同步时只发送这些用户声明与本次分析需要的最小上下文，API Key 由 Keystore 保护；Android UI 不直接调用网络或 DAO。
- 最近分析在手机作为可重新生成的派生缓存保存；同步在首个桌面网络请求前完成新分析持久化，桌面暂时不可达不会让本次结果丢失。
- facts 必须来自同步证据；inferences 必须带 confidence 和 evidenceRefs。学习时长只说明投入，不代表知识掌握。
- 自评题始终是 draft，不写入 approved 题库、`assessment_results` 或 `student_knowledge`。TeacherAgent 只读展示，并与既有 approved 题库正式诊断明确分区。
- TeacherAgent 把分析当作不受信同步侧数据；只有 `sourceSnapshotId` 与当前快照绑定且结构校验通过才展示。Teacher UI 不直接访问数据库或 Provider。
- 本例外不引入账号、云端数据库、公网同步、后台上传、云端学生画像、自动采纳计划或移动端完整辅导能力。

### 网络限制说明（必须展示给用户）

学校、公司和公共 WiFi 可能存在 AP isolation、VLAN 或防火墙限制；局域网同步只能在同一私有局域网内使用，不能宣传为任意网络下均可使用。Windows 防火墙阻止时给出明确诊断。
